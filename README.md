# Кейс № 5. Аналитический обзор приложения Django

## Техническое задание

Выбрать одну из кейс-задач № 1–4, оценить реализованное решение по девяти критериям и предложить способы устранения выявленных ограничений. Для обзора выбран [кейс № 3 «Приветствие на Django»](../case_03_django/README.md).

## Что реализовано

Приложение принимает имя из формы на главной странице. После проверки Django сохраняет имя в SQLite и перенаправляет браузер на главную страницу, где отображается приветствие для текущей сессии. При ошибке пользователь остаётся на форме и видит причину отклонения значения.

## Оценка решения

| Критерий | Результат анализа |
| --- | --- |
| Функциональность | Имя «Анна» сохраняется в SQLite и выводится в приветствии. Настроен переход POST → GET, поэтому обновление страницы сохраняет приветствие и оставляет в таблице одну запись. Пустое имя, пробелы и ввод длиннее 100 символов отклоняются. Новая сессия начинает с пустой формы без чужого приветствия. |
| Производительность | При валидной отправке приложение записывает одну строку. Для отображения приветствия приложение ищет её по первичному ключу. В серии из 20 последовательных локальных GET-запросов с сессией медиана времени ответа составила 47,7 мс. Измерение выполнено на сервере разработки Django через loopback и описывает только этот сценарий. |
| Удобство использования | На странице находятся подписанное поле имени и одна кнопка. Сообщение о незаполненном поле расположено рядом с ним. При ошибке введённое значение сохраняется в форме. |
| Безопасность | Django проверяет CSRF-токен при POST. Запрос без токена вернул HTTP 403. Строка с тегом `<b>` отобразилась как обычный текст. В подписанной сессии хранится идентификатор записи, а само имя находится в базе. Настройки рассчитаны на локальный запуск. |
| Масштабируемость | SQLite упрощает запуск на одном компьютере. При росте числа одновременных записей потребуется проверить конкуренцию за запись и при необходимости перейти на PostgreSQL. По мере накопления имён понадобится определить срок хранения записей. |
| Сопровождаемость | Модель, валидация формы, обработчик, шаблон и стили расположены в разных файлах. Миграция восстанавливает схему на чистой базе. В README есть команды установки, миграции и запуска. |
| Переносимость | Использованы Python, Django и SQLite. В коде нет абсолютных путей к базе, шаблонам и стилям. Проверка выполнена в Linux на Python 3.12 и Django 5.2.19. |
| Качество кода | `ModelForm` переиспользует ограничения модели. Представление проверяет форму, сохраняет запись и выбирает ответ. Операции с данными выполняются через ORM. |
| Тестирование | Через HTTP проверены GET страницы и CSS, сохранение имени, переход после POST, обновление страницы, изоляция сессий, отклонение пустого и слишком длинного ввода, HTTP 403 без токена и экранирование HTML. Записи отдельно сверены запросом к SQLite. Команда `manage.py check` завершилась без ошибок. |

## Ограничения и доработки

1. **Накопление данных.** Установить срок хранения имён и добавить команду удаления просроченных записей. Для автоматической очистки понадобится хранить время создания записи. Это расширение исходной модели при изменении требований.
2. **Параллельные запросы.** Провести нагрузочную проверку смешанных GET и POST. Измерять 95-й процентиль задержки и долю ошибок записи. Если SQLite создаёт узкое место, перенести данные в PostgreSQL и повторить измерения.
3. **Публичный запуск.** Вынести параметры развёртывания в окружение, установить постоянный секретный ключ, выключить `DEBUG`, задать допустимый хост и включить HTTPS с защищёнными cookie. Проверить CSRF после развёртывания. [Рекомендации по развёртыванию Django 5.2](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).
4. **Регрессии.** Добавить в CI проверки через Django Test Client, включая отдельный клиент с `enforce_csrf_checks=True`. Начать со сценариев сохранения, повторного GET, пустого поля и запроса без токена. [Документация Django 5.2 по CSRF](https://docs.djangoproject.com/en/5.2/howto/csrf/#testing-and-csrf-protection).
